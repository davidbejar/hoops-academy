# ADR-0051: Two services outside the JVM: academy finance in Go, a PDF renderer in Rust

- Status: Accepted (decision only: nothing built yet; no work package planned)
- Date: 2026-11-15
- Amends: ADR-0003 (Quarkus stays the stack of core, game and athlete, no longer of every backend service), ADR-0007
  (three services become five deployables once both are built)
- Related: owner decision of 2026-11-15, ADR-0002 (monorepo), ADR-0006 / ADR-0011 (RLS and tenant binding), ADR-0017
  (audit trail), ADR-0031 / ADR-0033 (gateway, rate limits), ADR-0034 (token audience per service), ADR-0036 / ADR-0037
  (events, roster replicas), ADR-0043 (security events), ADR-0045 (SAST / DAST gates), ADR-0046 (observability),
  ADR-0048 (exports; decision 67: "PDF later"), `docs/roadmap.md`

## Context
Hoops Academy is a learning project (ADR-0025). The owner wants features written in Go and in Rust **without
refactoring the existing code**. The architecture allows that only for new deployables: each service owns its schema
and database roles, the OpenAPI contracts in `libs/contracts` are language-neutral and the Dart clients are generated
from them, the gateway routes by path, Keycloak issues one audience per service, and core publishes the roster to
Redpanda. What a non-JVM service does not get is `libs/common-quarkus` (tenant binding, authz, Problem+JSON, paging,
replica consumer, security events) and the JVM test harness (`RlsSchemaMetaTest`, `GenericRlsIsolationTest`, ArchUnit,
JaCoCo gates, PIT).

Two candidate features have no code today and no dependency from the three services:
- **Academy finance**: an academy's administrators track incomes and expenses. Not in `docs/SPEC.md`; a new bounded
  context.
- **PDF output**: printable sheets were deferred by decision 67 (ADR-0048).

Tenant billing (the platform charging academies) was considered and left out: its seams (`billing.plan`,
`billing.tenant_subscription`, the `EntitlementService` port) live inside core, so a separate service would share
core's tables or put a synchronous call into every team and player creation.

## Decision
**1. Two new services, each in one language.**
- `finance-service` in **Go**: tenant-facing, owns the schema `finance`.
- `pdf-service` in **Rust**: stateless renderer, owns no data.

Both live in the monorepo under `services/` (ADR-0002), outside the Maven reactor. core, game, athlete and
`libs/common-quarkus` stay on Java and Quarkus and are not rewritten. The rule is "a new bounded context may choose Go
or Rust"; it is not a licence to move existing code. Still no Node anywhere.

**2. `finance-service` (Go).**
- Scope: fee plans per team or category, dues per player and period, payments **recorded by hand**, expenses by
  category, a season balance, CSV export by the spec of ADR-0048. No online payment collection and no payment
  provider.
- Data: schema `finance`, roles `finance_app` (non-owner, no `BYPASSRLS`) and `finance_migrator`. Every table carries
  `tenant_id uuid not null`, `ENABLE` + `FORCE ROW LEVEL SECURITY` and a policy on `app.current_tenant()`, created with
  `app.enable_tenant_rls`. The tenant is bound inside each transaction (ADR-0011).
- Roster: players, teams and guardians come from core's events as a replica behind a port, by the rules of ADR-0037
  (idempotent upserts, soft removals, parked invalid events). No REST call into core for roster data.
- Authz: in the application layer; non-members get 404, never 403. The roles and the rows of
  `docs/domain/authz-matrix.md` (at least: ADMIN manages; a parent reads only the dues of a linked player) are fixed in
  the work package brief, and the matrix stays the oracle of the role tests.
- API: `/api/finance/...`, contract first in `libs/contracts`, responses validated against it in tests, Dart client
  generated by `just gen-api`. Errors as Problem+JSON without stack traces.
- Platform conventions kept: its own token audience (ADR-0034), a gateway route with rate limits (ADR-0031, ADR-0033),
  audit records for writes and exports (ADR-0017), `hoops.security` events and `hoops_authz_denied_total{kind}`
  (ADR-0043), traces and logs over OTLP (ADR-0046), SASL user and ACLs on the broker and a NetworkPolicy (ADR-0036).

**3. `pdf-service` (Rust).**
- Renders printable sheets (first candidates: match sheet / box score, team roster). It connects to **no database and
  no broker**: the caller sends the data to print, already authorised and loaded where it came from, and gets a PDF
  back. So the service can never be a path to another academy's data.
- It is not an open renderer: it validates the JWT with its own audience (ADR-0034), sits behind the gateway with a
  rate limit and a body limit, renders only fixed templates (no caller-supplied markup, fonts or URLs, no network
  fetches while rendering), and answers Problem+JSON.
- Labels follow the user's language (es / en / id) as in ADR-0048; file names by the same pattern.

**4. The non-negotiable rules apply unchanged; their tooling is rebuilt per language.**
- TDD, clean code, secrets never in git, verification before completion: as today.
- Tenant isolation for `finance`: a schema meta test and a generic isolation test equal in strength to
  `RlsSchemaMetaTest` and `GenericRlsIsolationTest`, never connected as owner or superuser. `just isolation-check` and
  `just db-role-check` (the commit and push hooks) cover the new service before its first endpoint is merged.
- Hexagonal layering (`domain` without framework imports → `application` → `adapters`) enforced by an automated check
  in each language, the counterpart of ArchUnit.
- Definition of Done: the same gates (coverage ≥ 80 % lines, ≥ 90 % in `domain`), run by `just test`, which then covers
  Maven, Go and Rust.
- Static analysis: `golangci-lint` with a committed configuration for Go, Clippy with warnings denied for Rust, plus
  each language's formatter check, as gates of `just test` and CI from the service's first commit (the counterpart of
  SpotBugs and of the PMD gate planned for the Java services).
- Supply chain and scanning: pinned toolchains and lock files committed, Dependabot for both ecosystems, the SAST
  gates of ADR-0045 and the dependency scan extended to both languages, an SBOM per image (ADR-0043), ZAP API scan of
  both services after the e2e journeys.
- Delivery: images built with Podman, charts in the umbrella chart behind a switch, Tilt resources, compose entries.

**5. Left to the work package briefs.** Frameworks and libraries (HTTP, SQL, Kafka client, OpenAPI tooling, PDF
engine), the migration tool for `finance` (file convention `V<nn>__<snake_case>.sql` kept), toolchain versions,
mutation testing for the rule code, how the web reaches `pdf-service` (directly through the gateway, or through the
service that owns the data), and the finance domain model (periods, currency per academy, partial payments, refunds).
A brief that settles one of these records it here as an amendment.

**6. Order.** `pdf-service` first: it brings a non-JVM toolchain through `just`, CI, images, Helm and Tilt with no
tenant data at risk. `finance-service` second, on that groundwork. Tenant billing stays on core's seams, in Java.

## Consequences
- Three toolchains in one repository (JDK, Go, Rust): longer CI, more pins to keep current, more for `just doctor` to
  check. The agent skills `quarkus-hexagonal-service` and `tenant-isolation-testing` do not cover the new services;
  each needs its own skill before agents work on it.
- Tenant binding, authz and the security events exist twice (Java in `libs/common-quarkus`, Go in `finance-service`).
  They can drift. The guard is black-box: the shared contract tests, `just isolation-check`, `just db-role-check` and
  the e2e journeys run against every service whatever its language.
- Fixes to cross-cutting behaviour (a new Problem field, a new security event kind, a header) must be made in up to
  three places.
- Finance data is sensitive (what a family owes and has paid): the parent visibility rule and the audit of reads by
  export need the same care as health data.
- `pdf-service` receives personal data in request bodies: nothing of it is logged or put on spans, and nothing is
  stored.
- `CLAUDE.md` ("Stack", "Commands", "Conventions"), `docs/architecture.md` and `docs/conformance.md` describe three
  Java services; they are updated by the work package that lands each service, not by this ADR.
- If a service is abandoned, it is removed whole (directory, schema, chart, route, audience); nothing in core, game or
  athlete depends on either.
